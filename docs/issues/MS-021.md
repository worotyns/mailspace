# MS-021: Authenticator App two-factor authentication

Priority: P0 · Status: identity/store slice implemented; HTTP/UI integration pending · Depends on MS-001.

The owner requires Authenticator App 2FA in addition to application passwords.
Use interoperable TOTP, with a reviewed maintained compatible library rather than
implementing an OTP primitive. Keep OpenPGP browser keys/passphrases completely
separate from login factors.

## Required behavior

- Per-user enrollment under Settings → Security requires current password
  verification, a local QR/manual setup secret and a valid first Authenticator
  code before enabling. Never use an external QR service.
- Once enabled, password alone cannot create a full session or access any mail,
  keys page, API, job or application panel. Pending challenges are scoped,
  short-lived, rate-limited and not usable as normal sessions.
- Bound clock skew, reject reused TOTP counters atomically, and consume challenge
  and recovery proof exactly once. Password changes, revocation and factor
  changes invalidate the appropriate pending challenges and sessions.
- Provide one-time high-entropy recovery codes; store only digests and show raw
  codes only at their explicit creation. Disable/regenerate requires password and
  a current factor or recovery proof. No mail-based bypass or public reset.
- Encrypt TOTP seeds with a separately backed-up installation keyring and
  user/purpose-bound authenticated encryption. Never log seeds, OTP/recovery codes,
  request bodies or authentication cookies. Missing key material fails closed.
- Define explicit operator-only recovery, migration and rollback before changing
  the schema. Resetting a password must not silently remove 2FA.
- Test two-user ownership, CSRF/Origin, enrollment expiry, invalid/replayed codes,
  concurrent use, recovery reuse, clock boundaries, restart, migration, rollback
  refusal, key loss and no full session before the second step.

Record the concrete trust/storage decision in the next ADR before implementation.
UI must have accessible labels/focus/errors and native form fallbacks. No 2FA
capability or completion claim until the actual integrated flow passes tests.


## Implemented identity slice (ADR-0040, schema 13)

The store supports password-version-bound pending challenges, atomic TOTP/recovery proof and session creation, session-bound enrollment, one-time hashed recovery codes, secure factor changes and operator-reset service behavior. Seeds are protected with the separate auth-keys keyring and user/purpose AAD. Password/revoke/factor changes invalidate old password proofs and challenges; NewSession refuses configured MFA users. RFC vectors, races/replay, clock/expiry, rate budgets, key loss, restart, owner boundaries and transactional rollback are tested.

The existing HTTP login and Settings do not yet expose this flow; the next slice must wire PasswordLogin/CompleteMFALogin, native setup/challenge/recovery UI, local QR response and explicit operator CLI recovery. Do not advertise MFA as usable from this foundation alone.
