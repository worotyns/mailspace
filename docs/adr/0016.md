# ADR 0016: Spaces own message timelines; email threads remain transport references

Status: accepted design · 2026-11-13. Supersedes the conversation-level grouping assumption in ADR-0011/SPACES and the three primary presentation tabs. This is the user-confirmed product direction; implementation is delivered in bounded slices.

## Product model

A Space is a named, described area of relevance, not an IMAP folder, mailbox account or email thread. Membership is many-to-many at individual-message level: one original email thread can contribute different messages to several Spaces, and one message can appear in several Spaces. A Space aggregates those messages into a chronological dialog. It does not copy/move remote mail or rewrite References/In-Reply-To. Original account/folder/UIDVALIDITY/UID or authorized outbox references remain beneath every displayed entry.

Spaces are the primary navigation. One unified timeline replaces Conversations/Classic/Calendar as peer modes. People and scoped labels filter that same timeline. A compact date-jump calendar helps orientation; Classic/provider folders remain an advanced fallback. No folder-only Sent silo: outgoing messages participate in the same message timeline. All reads still authorize the current source, account revision and membership before presentation; relevance is never an ACL.

## Reply UX and routing

Reply selects one concrete source message and shows the target person/subject/account above an inline composer. A Space is not an SMTP recipient and cannot become an invented email thread. Sending derives the original parent references and verified From server-side. User-entered unencrypted replies are available inline with an explicit Send unencrypted action. Encryption is a simple lock option with a small unlock/recipient-readiness modal when needed, not a separate mandatory workflow. An encrypted source cannot silently become a plaintext reply. Key management remains an advanced setting, private material stays browser-only, and encryption errors never downgrade automatically.

A reply composed in a selected Space is assigned there by that explicit user action. It is not automatically broadcast to every Space containing the parent. Duplicate/unknown SMTP-result handling and nonces remain mandatory. Immediate outgoing entries must display accepted/rejected/unknown state honestly; transport acceptance is not delivery.

## Descriptions, manual triage and decision model

A Space description is its editable classification brief. Illustrative Space descriptions:

- Payments: payments, payment infrastructure and billing partnerships.
- Commerce: partner/affiliate/loyalty programs and e-commerce.
- Personal: meetings, cinema, insurance, home/apartment and electricity/water/gas bills.

Without a provider, an Unsorted screen supports manual message assignment to one or several Spaces. It is a functioning workflow, not a disabled AI demo. An optional decision model may propose assignments from these briefs; OpenRouter is one possible adapter, not a mandatory dependency or automatic activation.

JEV owns a bounded, versioned decision contract: input/source id and revision, allowed Space definitions/revisions, explicit provenance/payload policy, proposed target ids, confidence and a short safe reason. A deterministic gate validates target existence, scope/current source ACL, input/description revision, manual overrides and idempotency before application. Unknown ids/operators, stale responses and malformed output fail closed. The model cannot send mail, select arbitrary recipients, create ACLs or call tools. Dry-run has no assignments; replay uses the captured response/versions rather than calling a stochastic model again. Trace stores safe ids/decisions, not mail bodies or secrets.

Classification can be orchestrated in the browser. No provider means no provider client/background requests/model/index startup. External classification needs explicit provider/payload configuration; encrypted mail defaults to permitted metadata only. Client-decrypted content cannot silently enter an automatic cloud batch, backend index, AI, log, trace or webhook. The per-fragment explicit consent boundary of ADR-0002/AGENTS still applies. Manual changes are authoritative and a late model response cannot silently undo them.

## Delivery order

1. Typed live message references, owner-scoped unified source feed and persistent message-level Spaces/labels/manual assignments, with two-user and stale-generation tests.
2. One timeline/manual triage/People/date jump and inline reply UX; original references preserved. Replace the visible main screen, not just folder labels.
3. Small browser encryption modal and optional reviewed JEV provider contract/adapter with dry-run/trace/replay. No fake connected-provider UI.
4. Team source/sharing ACL integration, then 1.0 readiness/backup/restore/upgrade gates. Optional providers/index/Drive/YunoHost do not become hidden core prerequisites.

## Persistence boundary

Assignments hold source identity references and metadata, not copied message bodies or decrypted material. Logical message identity must be scoped to account/configuration revision and resist duplicate/ambiguous Message-ID values; physical IMAP locators remain individually authorized. Moving/copying a message between IMAP folders is not the same as creating a Space assignment. A source change/revocation cannot transfer old sharing/classification rights to a newly connected mailbox. Details and migrations belong to each implementing slice, not this design-only ADR.
