# ADR 0014: Encrypted local drafts and small client attachments

Status: accepted · 2026-11-13. Extends the MS-006 alpha; full compatibility remains gated separately.

## Attachments

The secure composer reads up to ten explicitly selected local files, at most 1 MiB total. Oversized selections fail before file reading; actual byte lengths are checked again while composing. A multipart/mixed MIME entity contains a UTF-8 base64 text part and base64 octet-stream attachments. Filenames use a single RFC 2231 UTF-8 filename* parameter, avoiding conflicting fallback/extended names. Control characters, paths and names over 180 UTF-8 bytes are rejected. Random multipart boundaries, CRLF and bounded MIME remain required. The whole entity is signed and encrypted locally, so attachment bytes and filenames never enter a plaintext upload. The server retains only its opaque multipart/encrypted envelope. This does not implement ordinary unencrypted attachment upload or the attachment Drive.

## Local persistence

Explicit Save encrypts a signed draft to the owner's verified From key only. Missing keys for eventual recipients do not prevent saving a private draft; they still block sending. The encrypted payload includes body, subject, recipients, hidden recipients, files, From/account binding, authorized reply locator and original send request nonce. The independent version-1 IndexedDB namespace is scoped to the opaque local user ID. Stored records contain only an opaque id, account id, signing fingerprint, update timestamp and armored ciphertext; list views do not persist/display plaintext subjects. Limits: twenty drafts and 16 MiB total ciphertext per local user. An existing record cannot be overwritten under another account.

Loading requires an unlocked key, a valid embedded signature matching the saved fingerprint, payload version/account/From checks and all composer limits. The restored content lives only in unnamed client controls/private JS memory inside hx-disable. No decrypted attributes, HTMX values, autosave, IMAP Drafts upload, backend database, model or index. Restored files remain local bytes and are explicitly listed/removable; new selections are checked against the same combined limits.

Lock, hidden tab, page departure, expiry and inactivity clear message/file controls and restored file references, while ciphertext drafts survive. JavaScript cannot guarantee physical RAM erasure. Initialization failures disable operations and lock rather than leave partially initialized controls without lifecycle protection. Server backups do not include browser vaults or drafts. Clearing site data/device loss removes these drafts; export key backups separately and do not promise server-side recovery or cross-device drafts in this slice.

## Send certainty

A loaded draft preserves its original nonce. New encryption is randomized, so a previously used nonce with different ciphertext conflicts rather than silently issuing another SMTP attempt. After an interrupted submission the user must inspect Outbox/provider. A confirmed successful queue response removes the active local draft; SMTP may still have unknown/rejected delivery, and its durable ciphertext/outcome remain in Outbox. There is no automatic retry on load, save, reconnect or application restart.

## Validation and migration

Node tests cover ciphertext-only persistence/reopen, lock, user/account isolation, scope tampering, quota bounds and overwrite behavior; composer/reader egress tests capture the actual handler requests, including attachment filename/content canaries. Unicode/binary attachment round-trips and GnuPG validate exact MIME bytes. Real browser checks cover explicit save, reload/unlock/load, missing-recipient block, send→Sent→decrypt and local Blob download compared byte-for-byte with the selected file, plus responsive dark UI. No server schema change. Keep the versioned local database intact when downgrading; no silent cleanup or migration to plaintext storage.
