# ADR-0035: Header-complete, scoped cached email threading

Status: accepted. Extends ADR-0016/0029 original-thread behavior without changing Spaces, source ACLs, reply targets or subject-only grouping policy.

## Correction

Some clients supply a direct parent in `In-Reply-To` while retaining an incomplete or different ancestor chain in `References`. Previously, the MIME preview ignored `In-Reply-To` whenever `References` was nonempty. Parse now retains a de-duplicated union: ordered References IDs, then additional In-Reply-To IDs. Parsing remains bounded to 64 IDs per header (128 combined) within the existing 64 KiB header limit. Header values remain exact; localized subjects such as `Siema` and `Odp: Siema` neither prove nor disprove a relationship.

The shared reference graph joins only explicit transport IDs. Two cached descendants citing the same uncached ancestor can share a thread container even when that ancestor lies outside the cache window. No ancestor message, body, sender, timestamp or reply target is fabricated or fetched. A referenced ID with multiple distinct cached messages is ambiguous and cannot link records, including through a missing-container shortcut. Same subject without reference evidence still stays separate.

The primary drawer graph is scoped to the selected account and connection revision, across that account's cached folders/outbox. The legacy folder conversation adapter is additionally scoped to account/folder/UIDVALIDITY. Neither graph can cross accounts or reconnect generations. Current source ownership/revision authorization still runs before reading raw mail or replying. The drawer still shows at most 100 cached related messages, not unlimited provider history.

## Existing cache repair

Preview JSON gains additive `ThreadingVersion: 1`. Freshly parsed mail includes it. Old cached previews with an existing ContentHash are repaired lazily when their authorized folder cache is read. SQLite selects a header prefix using delimiter searches bounded to the first 64 KiB; no MIME body is decoded, normalized, hashed again, indexed, decrypted or exported. Existing legacy ContentHash initialization retains its previous separate behavior.

At most 500 cache rows are considered per existing `Messages` call. Current-version previews do not select raw/header material or write anything. Legacy repairs are gathered while reading, the cursor is closed, and changes commit in one bounded transaction. Every update compares the original preview and header prefix, plus current owner/account revision and mailbox UIDVALIDITY. A concurrent source/preview/generation change aborts the whole repair instead of overwriting newer data. No remote IMAP request is made by repair or thread opening.

Repair changes References and ThreadingVersion only. It preserves cached Text, encrypted status, ContentHash, Message-ID, raw MIME, account/source locators and logical message identity. Existing Space/label/archive membership, manual revisions and decision identities therefore remain attached to the same messages. No new SQL schema/index/service or classifier call is required. A cold legacy folder can incur up to 500 bounded header inspections and metadata updates; subsequent reads avoid that repair path.

## Compatibility and rollback

Legacy presentation-only conversation IDs now include account scope to avoid collisions; canonical source/message identities remain unchanged.

An older binary ignores the additive JSON field and can read repaired reference lists. It may lose missing-ancestor grouping, but does not need a database rollback for this metadata addition. Full database/keyring backups remain part of normal upgrades. Malformed/truncated header prefixes are left unchanged; missing References/In-Reply-To, unsupported proprietary conversation identifiers and history outside the cache can still prevent a complete thread. Subject heuristics are deliberately not a fallback.

Tests cover mixed References/In-Reply-To, folded headers, shared uncached ancestors, duplicate ambiguity, unrelated identical/localized subjects, cross-account/revision/folder isolation, unchanged body/hash/source identity, no provider calls, idempotent repair and CAS refusal after source/preview/owner changes.
