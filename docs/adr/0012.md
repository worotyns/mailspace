# ADR 0012: Local OpenPGP key vault and explicit recipient trust

Status: accepted · 2026-11-13. Scope: MS-005, not complete mail crypto.

## Library and compatibility profile

Use OpenPGP.js 6.3.2 (LGPL-3.0-or-later), pinned in the asset lockfile. It provides maintained browser-native OpenPGP without a server crypto service. Its standalone module and source map/preferred sources are served locally; full LGPL/GPL texts and bundled dependency notices accompany it. idb 8.0.4 (ISC) supplies the small IndexedDB wrapper. No runtime CDN, keyserver or model. GnuPG interoperability is checked against an isolated keyring, not the user's existing installation data.

New keys use version 4 Curve25519Legacy, a two-year expiry, SHA-512, protected secret packets and the interoperable integrity-protected encryption profile. AEAD is not enabled in this profile. No insecure packet/signature exceptions or unauthenticated decryption are allowed. OpenPGP.js defaults are included in full before our explicit bounds: 4 MiB decompression, bounded Argon2 memory and imported armor size. This is a compatibility profile, not a claim that every Thunderbird/GnuPG version or all imported hardware stubs work. Mail MIME and Thunderbird acceptance remain MS-006 gates.

## Storage and lifecycle

The authenticated opaque user ID scopes a versioned IndexedDB database. It contains passphrase-protected secret-key armor, public keys and explicit email→fingerprint bindings. No private-key HTTP API exists. Passphrases and unlocked key objects exist only in private JavaScript memory; no localStorage, DOM attributes, event payloads or serialization exposes them. Private export always returns protected armor, even while unlocked. Clear imports require a new passphrase of at least 12 codepoints. Already protected imports must unlock successfully before persistence. Mixed clear/protected secret packets fail closed: re-export with consistent protection in GnuPG rather than persist any unprotected subkey.

The revocation certificate produced during generation is intentionally not stored beside the key. It is a transient explicit download and is discarded on lock. The user must export both a protected secret-key backup and the revocation certificate to separate safe storage. Browser data clearing/device loss is otherwise unrecoverable; the operator cannot reset a key's passphrase.

Lock drops references on explicit action, five minutes of inactivity, hidden document, page departure, session expiry, and a metadata-only same-origin BroadcastChannel signal on login/logout. Epoch checks prevent an in-flight unlock/generation from restoring state after lock. JavaScript cannot promise physical RAM zeroization, protection from a malicious browser extension, compromised OS, or malicious operator-supplied application code. HTTPS and a trusted delivered client remain necessary; a future signed desktop agent needs a separate ADR.

## Discovery is not authorization

Public import only discovers a key. Binding an email requires typing the full fingerprint and validating a current self-certified identity, primary key and encryption subkey. Expired/revoked/unusable keys are rejected. A changed fingerprint requires a separate replacement acknowledgement. Even a generated own key is not silently trusted for an email. Address domains are normalized to lowercase while local-part case is preserved. No WKD/Autocrypt lookup or network discovery runs in this slice.

## Browser boundary

The native /keys page has connect-src 'none' and form-action 'none', local scripts/styles only, no forms and no named private controls. Its region is hx-disable with history disabled. The client vault has no fetch or backend adapter. The rest of the application still serves ordinary mail; capabilities expose localKeyVault=true but openpgp=false until encrypted mail works end to end. This distinction prevents a key-management page from being advertised as finished OpenPGP mail support.

## Validation and rollback

Node tests exercise the exact bundled assets with IndexedDB emulation, a throwing network stub, protected persistence/reopen/export, passphrase failures, namespace isolation, lock races, trust replacement, expiry/revocation and mixed protection. A real GnuPG subprocess checks bidirectional signed encryption and protected secret-key import/export using a private temporary home. Browser checks cover secure-context gating, generation, unlock/reload/lock, blank passphrase fields, responsive dark UI and absence of named/form-owned secret controls. HTTP tests assert no key upload route and restrictive CSP.

No backend schema migration. Removing the feature must not silently delete local key backups; export before clearing the versioned browser database. Future vault format changes require an explicit migration and failure recovery strategy.
