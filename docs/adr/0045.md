# ADR-0045: Team source grants foundation

Status: accepted as the first MS-009/MS-010 slice. Enforcement is not wired yet.

Organizations currently grant no private-mail access: every timeline, attachment and job query is owner-scoped. Sharing needs an explicit, revocable, deny-by-default authorization layer before any team read path exists. This ADR defines that layer and adds its schema and service. It does not yet serve team mail, and no member gains access from this slice.

## Model

A grant authorizes exactly one provisioned user (`grantee`) to read one account owned by another user (`grantor`) inside one organization (`workspace`). It stores `workspace_id`, `account_id`, `mailbox`, `grantor_id`, `grantee_id` and `can_download`. An empty `mailbox` means every folder of that account; a non-empty value means only that exact folder, so a folder grant never widens to another folder.

Membership is not access. Organization membership, a Space rule, a label, a model/relevance match, thread membership or a provider folder never by themselves disclose private mail. Only a current grant row does, and only together with current membership on both sides.

## Authority and lifecycle

Only the current account owner may create or replace a grant; the caller never supplies a grant id. The grantee must be a provisioned user and a current member of the named organization, and self-grants are rejected. Unknown organization, foreign account, unknown user or a non-member grantee fails closed with no row written. `source_grants` is unique on `(account_id, mailbox, grantee_id)`, so re-granting updates `can_download` instead of duplicating.

Revocation deletes the row and is immediate. Every authorization call additionally rechecks, in one query, that the grantor still owns the account and that both users are still members of the organization. Removing a member, removing the grantor, or a changed account owner therefore blocks the next read even before the row is cleaned up. Deleting the account or organization cascades the grant away.

## Deliberate limits

- `can_download` is stored but not yet enforced; the enforcement slice gates attachment/raw download separately from metadata reading.
- No OpenPGP keys, passphrases, decrypted material, provider credentials or send-as permission can be represented by a grant. Separate send-as remains a distinct future decision.
- No public share links, no cross-instance federation, no inherited Space visibility.
- Provider/model requests, rules and jobs keep their existing owner scope; a grant is not an input to any automatic rule or model call.

## Enforcement (next slice)

The team read path will resolve a session user to its owned accounts plus currently valid grants, then require `Authorized` on every timeline page, message resolve, raw/attachment download, thread drawer, export and job. Management UI/endpoint will list, create and revoke grants for the session owner only. Tests must show two-user denial for every widened path, revocation and membership-removal blocking, scope/account/revision enforcement, and no grant leaking into another user's management list.

## Rollback

Migration 014 is forward-only; restore from the pre-upgrade database backup to roll back. Dropping `source_grants` returns the installation to deny-by-default, and the nullable `message_collections.workspace_id` column is ignored by older builds that never read it. No existing personal read, account, credential or collection row changes meaning.
