# ADR-0045: Team source grants foundation

Status: accepted. Deny-by-default grant foundation, read-only team enforcement and the owner-only grant manager are implemented; per-user team state and send-as remain open.

Organizations currently grant no private-mail access: every timeline, attachment and job query is owner-scoped. Sharing needs an explicit, revocable, deny-by-default authorization layer before any team read path exists. This ADR defines that layer, adds its schema and service, and enforces it on the read paths.

## Model

A grant authorizes exactly one provisioned user (`grantee`) to read one account owned by another user (`grantor`) inside one organization (`workspace`). It stores `workspace_id`, `account_id`, `mailbox`, `grantor_id`, `grantee_id` and `can_download`. An empty `mailbox` means every folder of that account; a non-empty value means only that exact folder, so a folder grant never widens to another folder.

Membership is not access. Organization membership, a Space rule, a label, a model/relevance match, thread membership or a provider folder never by themselves disclose private mail. Only a current grant row does, and only together with current membership on both sides.

## Authority and lifecycle

Only the current account owner may create or replace a grant; the caller never supplies a grant id. The grantee must be a provisioned user and a current member of the named organization, and self-grants are rejected. Unknown organization, foreign account, unknown user or a non-member grantee fails closed with no row written. `source_grants` is unique on `(account_id, mailbox, grantee_id)`, so re-granting updates `can_download` instead of duplicating.

Revocation deletes the row and is immediate. Every authorization call additionally rechecks, in one query, that the grantor still owns the account and that both users are still members of the organization. Removing a member, removing the grantor, or a changed account owner therefore blocks the next read even before the row is cleaned up. Deleting the account or organization cascades the grant away.

## Deliberate limits

- `can_download` is stored but not yet enforced; the enforcement slice gates attachment/raw download separately from metadata reading.
- No OpenPGP keys, passphrases, decrypted material, provider credentials or send-as permission can be represented by a grant. Separate send-as remains a distinct future decision.
- No public share links, no cross-instance federation, no inherited Space visibility.
- Provider/model requests, rules and jobs keep their existing owner scope; a grant is not an input to any automatic rule or model call.

## Read-only enforcement (implemented)

The timeline service resolves the viewer to owned accounts plus currently valid grants (`ListForViewer`) and resolves one source (`ResolveForViewer`). Shared records carry `Shared`, `SharedBy` and `CanDownload` and are read-only. Shared scopes never read the owner's local outbox. A folder-scoped grant covers only that folder; a whole-account grant covers the account. Shared mail appears in All activity and Unread but is excluded from the Unsorted triage count and view, and the UI omits reply, archive, label and Space controls and the read-state toggle while showing a `shared by` badge. A grantee never sees another owner's Sent copy labelled "You": the row names the real sender instead.

`/api/messages/raw` (original MIME and attachments) requires `can_download`; without it the grantee reads only cached preview text and cannot open the full raw reader. Every mutation keeps using the owner-scoped `List`/`Resolve`/service calls, so a grantee gets 404 for read-state writes, archive, Space/label membership, the assignment page and replies — no grant widens a write path. Rules, decisions, bulk actions and jobs keep the owner-scoped path and never see granted mail. Tests cover two-user denial for each of these paths, folder scope, outbox exclusion, download gating, revocation and membership-removal blocking, and the owner's own list staying unmarked.

## Grant manager (implemented)

`GET /sharing` is an owner-only settings panel that lists the session owner's active grants (member, organization, account, folder scope, download) and creates or revokes them with CSRF/Origin checks. It lists only grants where the caller is the grantor, so another user never sees or revokes them. Creation failures use one generic message for an unknown user or a non-member, so the panel is not a user-enumeration oracle; self-grants and invalid mailbox values are separate input errors. No grant is created for a foreign account, unknown organization or non-member recipient.

## Remaining (next slices)

Per-user team state: unread, labels/tags and assignment scoping (MS-010). Separate send-as stays a distinct decision and is not representable by a grant. No export path is widened before its own review.

## Rollback

Migration 014 is forward-only; restore from the pre-upgrade database backup to roll back. Dropping `source_grants` returns the installation to deny-by-default, and the nullable `message_collections.workspace_id` column is ignored by older builds that never read it. No existing personal read, account, credential or collection row changes meaning.
