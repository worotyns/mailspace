# ADR 0011: Usable workspace navigation, appearance and mail calendar

Status: accepted · 2026-11-12.

## Product navigation

Accounts are existing IMAP/SMTP identities; folders are server mailboxes. An organization is a membership/permission context. A Space is a view of conversations populated by explicit selection and deterministic autofilters. Spaces can eventually be private or organizational. The demo's former channel filters are labeled Spaces; they are fixtures, not a deployed rule engine or shared mailbox.

Matching a Space rule must never grant an ACL. A private Space can select the owner's mail; a team Space can select only already-shared threads or an explicitly authorized shared mailbox. Organization membership alone never grants access to private provider credentials, inbox, outbox or send-as. Rule matching, read sharing and send-as remain separate permissions. No public links, public plugin API, automatic model or decrypted-content rule input. Detailed contract: SPACES.md.

## Identity foundation brought forward

At the user's request, profile and organization navigation are implemented before browser crypto, so visible navigation is functional. Migration v5 adds display name/timezone, workspaces, membership, active preference and metadata-only membership audit. The workspace owner is explicit and immutable in this slice. Only that owner can rename/add/remove members; the owner cannot remove itself. Users must already have local logins. No signup or invitation email is introduced. Up to 20 owned organizations and 200 members each bound this foundation.

Every organization read/switch requires membership; every mutation requires session/Origin/CSRF. Removing a member blocks subsequent reads/switches immediately, and its saved active context falls back to Personal. Personal sessions and private mail ownership are unaffected. The active organization is a navigation preference, not an authorization token. Full mailbox sharing, thread shares, tags and Space rules remain MS-009/MS-010 follow-ups. Audit stores actor/target ids and fixed action names, never mail or provider secrets. Profile edits can change only the authenticated user's name/timezone; login email and credentials remain separate.

## Calendar and appearance

Calendar is a third presentation of cached mail received dates beside Conversations and Classic. It groups individual messages in an IANA timezone, provides month/day navigation and opens the same authorized thread. It does not fetch calendar events or create a content index. Recent-mail cache limits remain visible. Personal profile timezone controls message date formatting and calendar default; explicit calendar timezone is a view parameter. UTC is the default for new users. Go tzdata is embedded for reproducible container behavior.

A local browser preference selects System/Light/Dark. It stores only that preference in localStorage; no identity, message or decryption state. A local CSP-compatible script applies the theme before stylesheet paint and listens for system changes. Tailwind semantic colors cover all native forms and mail panes. The app uses one viewport shell; sidebar, feed and thread own their scrolling. Native settings/compose pages scroll normally. Keyboard/focus, narrow windows, low-height desktop and reduced-motion behavior remain required checks.

## Reproducible development sandbox

make dev-sandbox starts the real personal application with numeric loopback HTTP, a loopback-only TLS synthetic provider, two generated local logins and a seeded organization. Random login passwords are private files, not production defaults or command-line arguments. Existing state never silently regenerates a missing login file. Outbound approval is restricted to the fixture endpoints; no real provider is contacted. The synthetic marker is explicit. The production image still builds cmd/mailspace only. Restart preserves app identity/settings, while fixture in-memory mail resets with new UIDVALIDITY. This is a developer preview, not a deployment profile.

## Rollback

Forward-only v5. Older binaries refuse the schema. Restore the complete matching offline database/keyring backup for rollback. Active workspace preferences never justify data access after a membership change.
