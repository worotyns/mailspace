# ADR-0040: Authenticator App TOTP and gated sessions

Status: accepted and implemented for MS-021. Integrated native login/Security/QR/recovery routes and local operator CLI are delivered; manual real-app/browser acceptance remains separate.

Use pinned pquerna/otp v1.5.0 (Apache-2.0) for RFC 6238 TOTP, configured for six digits, SHA-1 and 30-second periods with at most one adjacent step of clock skew. This interoperable OTP profile is independent of OpenPGP signing algorithms. Its boombuler/barcode dependency is MIT and generates QR locally; no external QR/SMS/email service is used. Neither module executes lifecycle scripts or requires a native/runtime provider. Upstream sources: [library](https://github.com/pquerna/otp/tree/v1.5.0), [release security fix](https://github.com/pquerna/otp/releases/tag/v1.5.0), [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238).

## Authentication boundary

MFA is enrolled per user. A successful password proof checks a users.auth_version inside the transaction that creates either a full session or a five-minute random, hashed, HttpOnly/SameSite Strict pending challenge. A pending cookie is never a session and cannot authorize mail, APIs or key pages. Challenge forms require exact Origin plus their own synchronizer CSRF. Up to five live challenges are allowed per user, with five attempts each and a persistent shared five-failures/five-minute factor budget across challenges and security actions. Existing bounded IP and concurrent-password limits remain in force.

TOTP step consumption, one-time recovery consumption, challenge removal and full session creation commit atomically. The last accepted counter must increase; races or replay cannot mint another session. Password reset, revoke-all and factor changes advance auth_version and revoke pending/full sessions atomically. Ordinary password-to-session creation also checks the verified version, closing the password-reset race. NewSession refuses a user with enabled MFA; trusted verified-factor paths use an internal transactional helper.

## Enrollment and secrets

Settings enrollment requires a current full session and current password. A ten-minute pending seed is bound to that exact session and auth version. Only a valid initial app code activates it. Activation, disable and recovery-code regeneration revoke existing sessions/challenges and create a fresh session after their required proofs. Disable/regeneration require password plus TOTP or a recovery code. Ten 160-bit recovery codes are displayed only on creation and stored as per-user SHA-256 digests; each is consumed once. A valid recovery code is an explicit alternative factor, not a silent password-only fallback.

TOTP seeds use the existing standard-library AES-GCM credential box with a **separate** auth-keys keyring beside the SQLite file and purpose/user-bound AAD. The credentialvault primitive is broadened only from server mail passwords to server authentication seeds; it still never accepts OpenPGP private keys, their passphrases or decrypted mail. Key material is created only on explicit enrollment. Reading an existing seed requires the existing complete keyring; missing/corrupt keys never generate a replacement or bypass MFA. Explicit valid recovery proof remains usable for recovery even if a TOTP seed key is lost.

Setup seeds/QR are available only during that session-bound pending enrollment. They are not accepted from hidden fields or arbitrary client secrets. Codes, seeds, recovery values, cookies and request bodies are never logged. QR is generated in memory; no secret appears in its URL. Pages/APIs are no-store and private HTMX history snapshots remain prohibited. Protected OpenPGP browser storage is unrelated to these server login factors.

## Storage, operation and rollback

Migration 013 adds auth_version and dedicated MFA configuration, recovery-digest and pending-challenge tables with owner foreign keys, limits and cascade deletion. Existing users remain password-only until explicit enrollment. Back up SQLite and the **auth-keys** directory together, separately from credential-keys/browser key exports. Missing auth keys fails closed for TOTP; restoring SQLite alone does not recover app codes. Operator-only `user reset-2fa EMAIL` explicitly removes that factor and revokes sessions; password reset alone never disables MFA. There is no public reset or email bypass.

Rollback requires the matching pre-migration database backup and binary; old binaries reject schema 13. Keep the installation keyrings when reverting, so newer encrypted rows remain recoverable after returning to a compatible version. Restore drills must revoke sessions/challenges so old authentication state cannot reappear unnoticed.

Tests must cover owner/session/CSRF/Origin boundaries, no full session before factor proof, counter/clock/expiry boundaries, concurrent replay, recovery reuse, rate budgets across new challenges, key loss, restart, migration/rollback refusal, password/reset/revoke races and secret redaction. Passing service tests alone does not advertise an integrated 2FA feature or complete 1.0.


## Integrated HTTP/UI

`POST /auth/login` uses the version-checked identity transaction. The second step `/auth/mfa` uses a separate `__Host-mailspace-mfa` cookie (loopback development uses the corresponding development name), its own synchronizer token and exact Origin. It cannot authorize normal routes even when its value is substituted into the full-session cookie. An explicit cancel invalidates the challenge after CSRF verification. Successful account switching revokes/clears the old full session before the factor step.

`/security` and `/security/authenticator/{setup,enable,cancel,recovery,disable}` use only the session owner; no submitted user ID selects the target. Their native forms enforce 4 KiB bodies, bounded IP attempts and shared password concurrency. The pending QR at a fixed `/security/authenticator/qr` URL is generated locally as a 256×256 PNG only after checking the exact enrollment session. The seed never appears in the URL. Recovery values are rendered only in the activation/regeneration response, never in API metadata or later GETs. Local UI cleanup removes pairing/recovery material on pagehide or private-state clearing/lock; native submit preserves proof serialization while broadcasting only a vault-lock event to other tabs. No authentication material is persisted in browser storage or cross-document messages. Server pages remain no-store, hx-disable and hx-history=false; no generic decrypted-mail boundary changes.

Security navigation opens a full native page (`target=_top`), outside the application panel allowlist. Factor changes rotate the session/CSRF; leaving an older parent timeline mounted could leave its forms with revoked CSRF, especially when a dirty inline draft suppresses the normal panel-close refresh. The Security page stays frame-ancestors 'none'. Returning to the timeline loads fresh session metadata through ordinary navigation.
